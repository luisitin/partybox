# I-083 · A face already in the room says so (option B)

Branch `b/I-083-B` reapplied by hand (`Join.tsx`, `Join.module.css` and `net/info.ts` conflicted
against I-031, I-076, I-079 and the owner's room browser; `app.ts` applied clean).

## What ships

- **A** — `/api/info`'s rooms carry the avatar ids in use; a taken face gets a small "IN" tag on
  its grid cell and an `aria-label` that says so. Still pickable — nobody is told their favourite
  is gone.
- **B** — a fresh phone's random default is drawn from the free faces; a remembered identity still
  wins.

Three adaptations to the current code, all forced and none a redesign: the branch read
`info.rooms[0]`, which ADR-043 (several rooms) made ambiguous — the room in the URL decides, and
`rooms[0]` is the fallback; the badge sits top-right instead of bottom-right, because I-079's
"this month" tag owns the cell's bottom edge; and the default face is **derived** rather than rolled
once in a `useState` initialiser. That last one is a bug the branch had and the recorded clip could
not show: `/api/info` — and with it the set of taken faces — lands a beat after the first render, so
a default rolled at mount knows nothing about the room. The first probe run caught a fresh phone
defaulting to Sam's owl. The default is now `chosen ?? pool[seed * pool.length]`, recomputed when
`taken` arrives; a remembered identity or a tap still wins.

## Proof

Scratchpad `c-capture/probe_I083.ts` — Sam joins on the owl, then six fresh phones open the join
page:

```
room avatars            ["owl"]
badged cells            ["owl (someone in the room has it)"]
six fresh defaults      robot, ghost, ghost, cat, lion, panda
any took a taken face?  false
```

Exactly one badged cell, the owl, and six independent fresh defaults none of which is the owl.
